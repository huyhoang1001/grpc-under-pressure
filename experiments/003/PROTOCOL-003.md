# PROTOCOL-003 — E3 Bidirectional Message/Outcome Contract

Status: Stage 0 v1.1, amendment A01 (client outstanding33; original v1.0 at commit000308b). Normative alongside EXPERIMENT-003.md and VALIDITY-003.md. This document specifies a protobuf schema, not implementation code.

## 1. Wire contract (schema specification)
Package `pressure.e3.v1`; service `OverloadService`; RPC `Exchange(stream ClientFrame) returns (stream ServerFrame)`. One stream per client in primary. ClientFrame oneof: `Work`, `CancelOriginal`, `ClientDone`; ServerFrame oneof: `TerminalOutcome`, `ProtocolError`. Client half-close is normal EOF and supersedes ClientDone; ClientDone optional for diagnostics, not necessary for progress.

Work fields: `run_id` (string), `message_id` (uint64, 0..2879 primary), `attempt_id` (uint64 unique per run), `attempt_number` (1..3), `client_id` (uint32), `scheduled_offset_ns` (uint64 from run epoch), `deadline_offset_ns` (uint64), `payload` (bytes, exactly 16384), `payload_sha256` (bytes, 32), `expendable` (bool, true primary). ServerFrame TerminalOutcome: `run_id`, `message_id`, `attempt_id`, `outcome` enum (`COMPLETED`, `REJECTED_OVERLOAD`, `DROPPED_OVERLOAD`, `EXPIRED`, `PROCESSING_FAILED`, `CANCELLED`, `DUPLICATE_RESULT`), `server_event_seq`, `server_event_offset_ns`, `worker_service_ns`, `detail_code`. `DUPLICATE_RESULT` carries the referenced original terminal disposition; it is never a new completion. ProtocolError carries correlated IDs when known and error code. Never interpret an uncorrelated stream status as per-message refusal.

A client request has exactly one application attempt ID. A server response has one terminal disposition for that attempt if delivered. Admission is a server-ledger event, not a required wire ACK. No ACCEPTED frame in primary. A successful grpc-go Send means only that grpc-go accepted a message for transmission, not that the server decoded or admitted it. gRPC stream status reports RPC/transport failure; per-message REJECTED/DROPPED are ordinary response frames on a healthy stream. Use RESOURCE_EXHAUSTED only for stream-wide resource failure, not normal policy refusal.

## 2. Timing and deadlines
Single-host primary with monotonic run epoch communicated in startup coordination and validated clock calibration; authoritative scheduled offsets from immutable workload manifest. The server receives absolute deadline information via calibrated epoch mapping; verify clock uncertainty below 5 ms or invalidate run. At equal deadline and completion timestamp, completion counts on time (`<=`). Never extend deadline for retry. Service delay selected by worker start time. Timers and event ordering are monotonic, not wall-clock adjustments.

At deadline: pending original expires locally; retry eligibility ends; server queued work is removed; running worker receives cancellation request and holds its permit until worker exit. Completion before or exactly at deadline is on-time even if ACK arrives later. A completion after deadline but before cancellation observation is late. Client cancellation is distinct from deadline expiry; server logs request, observation and termination separately. Cancellation does not undo completed work. Cancellation of a stream requests cancellation for its unfinished admitted originals, not retroactive failure of completed ones.

## 3. Ownership and lifecycle
Original: SCHEDULED -> CLIENT_PENDING -> ATTEMPT_OUTSTANDING -> (SERVER_ADMITTED -> SERVER_QUEUED -> RUNNING -> COMPLETED / EXPIRED / FAILED / CANCELLED) or REJECTED / DROPPED; original can also become CLIENT_BACKLOG_EXHAUSTED or EXPIRED_BEFORE_SEND. RETRY transitions REJECTED_ATTEMPT -> RETRY_WAIT -> ATTEMPT_OUTSTANDING; original remains same. One active attempt per logical ID, with new attempt ID each retry. At the final cutoff, UNKNOWN is permitted only with evidence of ambiguous delivery; it is not silently rejected.

Server admission is atomic: validate identity/deadline; check dedup; reserve outcome capacity; acquire one admission permit; register admitted ownership; enqueue FIFO or start worker. A duplicate of active/admitted/completed logical work never creates a second worker. Previously rejected attempts may be retried and admitted; refusal doesn't reserve an admission slot. Release permit only when queued work is actually removed or worker has exited. Cancellation request alone never releases a permit.

## 4. Fixed bounded resources
Client original pending capacity = 32; client outstanding attempt credits = 33, acquired before attempt send and released on terminal response or definitive stream closure/reconciliation; retries share the same bounded pending capacity and are not privileged over new originals. Client response event channel = 64; receive loop updates the attempt ledger without waiting on the sender or retry scheduler. Retry timer heap max 32 eligible pending entries (shared pending budget), no detached per-attempt timers. Full pending budget at original arrival yields CLIENT_BACKLOG_EXHAUSTED; at retry scheduling yields REJECTED_FINAL if still before deadline, otherwise expiry. Every such event is logged.

Server total admission permits = 32, including queued, running and cancellation-pending. Exactly one worker. Server decoded request staging <=1. Server terminal-response reservations = 32 for admitted messages, allocated at admission and retained until the terminal frame is accepted by writer or the stream fails; immediate-response queue = 32 for rejection/drop/expired/duplicate responses. Server response writer is independent and never acquires admission permits. When immediate response queue is full, receiver must stop decoding; no unbounded spill. Bounded response queue pressure may temporarily delay admission decisions for REJECT/DROP and is measured, not hidden. Every blocked wait supports cancellation.

**Deadlock rule:** Client receive loop never waits for send credits; server writer never waits for admission; server worker never waits for client ACK; server receiver never holds a permit while waiting for an unreserved terminal-response slot. The server may reserve a terminal slot before permit acquisition, but releases unused reservation on refusal or cancellation. Do not couple release of admission permits to delivery of ACKs. A terminal response can be pending while the permit is already released, with reservation still counted.

Blocked local server-side outbound progress: when a server response write is blocked, it may remain without local outbound progress for at most 1 second (frozen `response_progress_timeout`); then cancel the stream and unfinished admitted work, record undelivered outcomes and terminate. This timeout does not guarantee detection of a client application that stops reading: transport buffers may accept responses without client application consumption. Successful server writes do not prove that the client application consumed the responses. T06 uses a deterministic server-writer barrier to simulate blocked local outbound progress and verifies the timeout, bounded buffering, permit cleanup and absence of deadlock. Do not introduce additional client acknowledgment mechanisms solely to detect stopped reads. Client send/receive tasks independently observe cancellation. No unbounded retry or notification buffering. Normal client send half-close does not stop response reading; server drains admitted work through terminal outcomes or deadline/cancellation, then closes cleanly.

## 5. Four policy semantics
WAIT: when permit unavailable, pause inbound reads after at most one decoded staging request and await admission or deadline/stream cancellation; client may block in Send and exhaust bounded credits. No server rejection for normal full budget. REJECT: nonblocking admission; full -> terminal REJECTED_OVERLOAD; no retry. RETRY: same server rule as REJECT; client retries only explicit REJECTED_OVERLOAD, max 3 total attempts, nonoverlapping, same deadline, backoff delay `uniform[0, min(100 ms * 2^(attempt_number-1), 400 ms)]` after refusal, with reproducible per-run/client seed. If retry cannot be scheduled in bounded pending capacity, record REJECTED_FINAL; no automatic retry for ambiguous ACK loss or transport errors. DROP: nonblocking admission; full -> terminal DROPPED_OVERLOAD if expendable; nonexpendable is protocol-invalid for primary and refused with explicit error rather than silently discarded. All policies enforce the same deadlines and cancellation.

## 6. Deduplication and ledger
Primary logical-ID index fixed capacity 2880, attempt-ID index fixed capacity 8640; at most 3 attempts per original. Both allocated for the run and retained through t=39 s and until all workers/attempts terminate or are marked unresolved. No eviction during run. Store hashes, state and offsets, not duplicated payloads. A new ID when logical ledger full or a new attempt when attempt index full is `METADATA_CAPACITY_EXHAUSTED`, recorded as safety failure and invalid primary run; never silently evict. Concurrent identity registration and admission atomic with respect to same ID. Same logical ID with changed payload hash, deadline, or client ID -> protocol violation. Duplicate while active -> return prior/linked terminal result when available, without starting worker; duplicate after completion -> replay result. Previously refused IDs may retry and acquire admission once. In-memory guarantees do not survive process crash; no exactly-once claim across restart.

Event logging uses bounded writer channel (capacity 1024), append-only per-process JSONL and flush at shutdown. A full event channel must block/cancel rather than silently drop events; prolonged blockage invalidates run. Measure ledger capacity, occupancy and allocated bytes on both sides. Event file sizes are reported separately from RSS.

## 7. Stream and ambiguous-outcome handling
A lost/delayed terminal frame never changes authoritative server execution. Client tracks CLIENT_OBSERVED and SERVER_RECONCILED separately. On stream error, stop new attempts, cancel outstanding work, wait bounded grace, reconcile from server ledger; mark any unreconciled originals UNKNOWN. Do not retry ambiguous delivery. Server response write success does not prove client received the frame. No detached worker survives stream cancellation beyond measured cancellation grace; if it does, mark run invalid. Terminal outcome frame and worker completion must have stable server event sequence IDs for correlation.

## 8. Required protocol tests
Deterministic barriers: blocked client reader, full response queue, full admission queue, blocked client Send, half-close, stream abort before decode, lost terminal frame, deadline while pending/queued/running, completion at deadline boundary, cancellation after completion, concurrent duplicate attempts, changed payload on reused ID, ledger capacity and logging backpressure. Every test checks boundedness, termination, permit ownership and event accounting. See VALIDITY-003.md for acceptance criteria.

## Amendment A01 — minimal client admission headroom

A01 changes only the client outstanding attempt-credit limit from32 to33 for every policy. With server admission fixed32,33 is the smallest integer limit permitting a conforming single client to submit an additional attempt to a full server. The choice follows ownership arithmetic, not observed policy performance. Pending capacity remains32 shared by originals/retries; server admission32, staging<=1, admitted-terminal reservations32, immediate responses32, client response events64 and event writers1024 are unchanged. The same limit applies to WAIT/REJECT/RETRY/DROP. Credit is acquired before Send and retained until a terminal response or definitive closure; deadlines and retries are unchanged.

At most65 originals can be client pending or outstanding (32+33), rather than64. One extra credit permits at most16384 additional bytes of distinct unacknowledged application payload; this is an ownership bound, not a bound on transport/allocator/process RSS. Server admitted-plus-staged payload remains at most33*16384 bytes. Transport windows remain65535; credits do not override HTTP/2 flow control or prove delivery. Immediate-response pressure still pauses decoding; no response buffers are enlarged.

Acceptance additionally requires a real Go scheduler/Rust tonic saturation fixture, respecting33 client credits and all other resource bounds, showing full-budget refusal for REJECT/RETRY and drop for DROP, real bounded retries, plus bounded/cancellable WAIT. A deterministic worker barrier is permitted only in labeled correctness fixtures; no fabricated policy outcomes or bypass of client credit enforcement. The34th simultaneous outstanding attempt must block, while pending/retry overflow and deadline behavior remain explicit.

All later run/configuration manifests (not the immutable original-identity workload file) must identify contract revision A01 and client_outstanding_limit=33. Pre-amendment Stage1/2 evidence remains unchanged and valid for its original correctness scope; it does not establish A01 saturation reachability. Future policy comparisons must use A01 identically for all policies, and must not pool results with the32-credit Stage0 configuration or attribute cross-revision differences solely to policy. Primary workload, server budget, hypotheses, analysis definitions and other research decisions are unchanged.
