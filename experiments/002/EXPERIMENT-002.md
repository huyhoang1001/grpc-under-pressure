# EXPERIMENT-002 — Adaptive Admission Inside One Client-Streaming RPC

**Status:** Stage 0 contract frozen for implementation; no Blog 2 measurements. **Scope:** one Go client, one long-lived client-streaming `Ingest(stream Payload) -> Summary` RPC, one Rust tonic handler, one serial Tokio worker. Compare admission budgets, **not** RPC concurrency or worker concurrency. Preserve E1 evidence unchanged.

## 1. Research question and hypotheses

Can adjusting the maximum number of *pending application messages* in response to downstream service health reduce server queue residence time and improve recovery while preserving bounded memory, worker throughput, and acceptable whole-workload completion time?

- **H1 (safety):** every policy satisfies physical queue depth `Q <= 32`; no message is lost or processed twice on normal completion. Any violation falsifies H1.
- **H2 (latency):** adaptive reduces per-message server queue-residence p95 by at least 20% versus fixed-32 during the prespecified slowdown/recovery window. A smaller or uncertain difference fails H2.
- **H3 (throughput):** adaptive worker completion throughput over the 36-second offered-load interval is at least 95% of fixed-32, and worker idle fraction during backlog is not materially higher. Failure falsifies H3.
- **H4 (recovery):** after service returns to 10 ms at t=24 s, adaptive returns to its healthy queue-delay band sooner than fixed-32 without increasing whole-RPC duration by more than 10%. Otherwise H4 fails.
- **H5 (added value):** adaptive provides a material latency/throughput/recovery tradeoff unavailable from fixed-8. If fixed-8 matches or dominates, do not claim adaptation is necessary.

**Null hypothesis:** adaptive budgeting mainly moves waiting upstream; fixed bounded admission is sufficient. Local queue latency alone is not an end-to-end latency claim.

## 2. Policies and workload (frozen)

| Policy | Physical Tokio MPSC capacity `K` | Logical pending-work budget `B` |
|---|---:|---:|
| `fixed32` | 32 | 32 |
| `fixed8` | 32 | 8 |
| `adaptive` | 32 | initial 16; range [1,32] |

All policies use the same admission gate and instrumentation; only `B` updates differ. One connection, one stream, one handler, one worker; no per-message spawned tasks, retries, compression, or retained processed results. Payload: 16,384 pseudorandom data bytes, deterministic seed 1, with monotonically increasing sequence IDs for attempted messages. Client pacing target: 80 scheduled slots/s for 36 s (2,880 scheduled slots). Server service schedule, measured from a common server-side *workload start marker*: `[0,12)` s: 10 ms sleep; `[12,24)` s: 40 ms sleep; `[24,36)` s: 10 ms sleep. Select the service delay **at worker service start**, not completion; record transition times. Server and client synchronize workload start with a runner-controlled barrier/marker and record actual offsets; reject runs with >100 ms phase-alignment error. Client never catches up missed scheduled slots; record them as skipped. Continue normal EOF/drain after t=36 s, with the 10 ms service setting retained. Same transport windows, resource limits, build mode, CPU placement, and collection intervals across policies; record exact values in manifests. One fresh server process per run.

## 3. Message states and permit semantics

`received`: `stream.message()` returned a complete `Payload`. `admitted`: payload successfully handed into the physical queue. `dequeued`: worker takes ownership. `processed`: worker finishes service successfully. `discarded`: previously admitted work terminally abandoned on cancellation/failure. Go `Send` success is **not** server admission or processing acknowledgment.

- `Q`: enqueued but not dequeued; `W`: worker-owned message (0 or 1); `R`: logical admission reservation acquired but not yet consumed by successful enqueue (0 or 1 per handler). Logical pending occupancy `O = Q + R`. Handler must acquire a logical reservation **and** reserve one physical MPSC slot **before** calling `stream.message()`; never prefetch a message while waiting for either. Acquiring a logical reservation increments `R`. Reserving physical capacity does not increment `Q`. On successful receive and `permit.send(payload)`, atomically transfer `R -> Q`, increment `received` and `admitted`, and account payload bytes. On EOF, error, or cancellation before enqueue, drop the physical permit and release `R`, without incrementing `received` or `admitted` unless a complete payload was actually delivered. If receive succeeds but handoff fails, count `received_not_admitted` and terminate with error; never silently drop it.
- On dequeue, atomically `Q--`, `W++`, move queued payload bytes to worker-owned bytes, and wake admission waiters. On successful service completion, `W--`, `processed++`; payload ownership ends. All state changes and metric snapshots must be consistent (one lock or equivalent atomic transaction). `R` includes any pending physical reservation; the single handler never holds more than one. A logical reservation cannot be acquired unless `O < B` **at the instant of acquisition**. On budget shrink to `B < O`, preserve all existing reservations/messages; acquire no new reservations until `O < B`. Do not revoke permits, discard work, or resize the physical channel. The safety invariant is `Q <= K`, and `O <= max(B, O_at_last_shrink)` until occupancy falls; `O <= B` is **not** required immediately after shrink.
- A physical slot may be freed on dequeue before the logical gate opens; both constraints must be satisfied before next receive. A budget of 1 constrains *pending* work, not the executing worker. `W` is excluded from `B`. Logical reservations have exactly one terminal outcome: enqueue or release. EOF detection may wait for pending capacity; it must eventually progress when the worker drains. Any worker failure or cancellation must wake all blocked admission waits.

## 4. Controller (frozen initial algorithm)

Tick every **500 ms** from workload start; no updates after terminal EOF/cancellation. Use completed service durations in the immediately preceding tick; if fewer than **5** completions, hold budget and reset threshold streaks. EWMA service duration in milliseconds: `S_hat = 0.2 * interval_mean + 0.8 * previous_S_hat`; initialize from the first eligible interval (until then hold initial B=16). Use queue occupancy `Q` sampled atomically at tick time, and `D_hat = Q * S_hat` (a proxy, not measured p95). Target 100 ms, high threshold strictly `>125 ms`, low strictly `<75 ms`. For increase demand, define `near_full = (Q + R >= B - 1)` at tick time; require at least one observed worker completion in the interval (already implied by eligibility).

- If `D_hat > 125 ms` for **two consecutive eligible ticks**, set `B = max(1, ceil(B/2))`, then clear both streaks.
- Else, if `D_hat < 75 ms` **and** `near_full` for **two consecutive eligible ticks**, set `B = min(32, B+1)`, then clear both streaks.
- Otherwise hold `B`. An ineligible tick resets streaks; an eligible tick not satisfying a condition resets that condition's streak. Decrease takes priority. Budget changes wake the gate. No special recovery override, manual tuning, or per-policy feedback differences. Record every tick: elapsed time, Q, R, W, B before/after, interval completions, interval service mean, EWMA, proxy delay, streaks, decision reason. Service-time feedback uses actual elapsed service, not configured sleep.

## 5. Measurements and invariants

Record server per-message monotonic enqueue, dequeue, and completion durations in bounded-memory histograms (or append-only streamed records), with p50/p95/p99 by predefined phases; `queue_residence = dequeue - enqueue`, `service_duration = completion - service_start`. Record gate wait (logical), physical-reservation wait, queue depth, reserved count, in-worker count, queue/handler/worker payload bytes, budget, worker busy/idle time, received/admitted/dequeued/processed/discarded/received-not-admitted totals, RSS, errors, active streams, connections, and service phase. Sample gauges/counters every 200 ms and capture controller ticks at 500 ms. Avoid per-message console logging in measured runs.

Server invariants (checked continuously and at terminal state): `Q = admitted - dequeued - discarded_from_queue`; `W = dequeued - processed - discarded_from_worker`; `0 <= Q <= 32`; `0 <= W <= 1`; `0 <= R <= 1`; `received = admitted + received_not_admitted` (if no handoff failure, received = admitted). Normal successful EOF/drain: `R=Q=W=0`, `admitted=dequeued=processed`, `discarded=0`, and final `Summary.accepted=admitted`, `Summary.processed=processed`. For terminal failure: `admitted = processed + discarded + Q + W`, with `discarded` counting only terminally abandoned admitted messages; at final cleanup `Q=W=0`. Count dropped worker-owned work once even if cancellation races completion. Never reset gauges before recording terminal disposition.

Client: record scheduled slots, skipped slots, attempted Sends, successful Send returns, failed Sends, `Send` wall duration histogram and >20 ms count, actual send-start/send-return timestamps relative to client monotonic workload start, send-blocked cumulative duration, client RSS, actual send rate per phase, time of half-close, final RPC status, final Summary, and total RPC elapsed time. `scheduled = skipped + attempted` for elapsed scheduled slots; `attempted = successful_sends + failed_sends` after all Send calls return. A blocked `Send` can cause future slots to be skipped; never create an unbounded client work queue. Measure actual delivered/processed work separately from nominal 80/s. Report upstream backpressure as Send duration and skipped slots, **not** an isolated HTTP/2 flow-control stall or end-to-end completion latency. Do not subtract client and server monotonic clocks to invent per-message end-to-end latency.

## 6. Lifecycle, validity, and decisions

Normal: run 36-second offered-load schedule; stop generating; client `CloseAndRecv` half-closes; server continues capacity-gated reads until EOF and drains the worker; return Summary only after all admitted messages finish. Deadline is **120 s from RPC creation, including send and drain**. On cancellation/deadline/worker error, unblock all waits, stop admission, abort worker, classify queued/worker work as discarded exactly once, release reservations, and record final counters and reason; a failed RPC must not be reported as a successful drain. A server cannot acknowledge or reject individual messages using the existing single-response client-streaming contract; whole-RPC failure is not per-message rejection.

**Valid primary run:** exact topology; matching source/binary and config manifest; phase-alignment error <=100 ms; correct invariants; no unexpected cancellation, deadline, safety abort, worker failure, or instrumentation gap; complete EOF/drain; workload schedule executed with skipped slots recorded (do not exclude merely because backpressure caused skips). Preserve invalid runs with reasons, never silently replace. Run **five valid fresh-process repetitions per policy** with randomized/interleaved order and fixed seed; report every attempted run, exclusions, medians, per-run distributions and uncertainty. Preserve raw phase-aware metrics and process samples.

**Primary comparison:** pooled per-message queue-residence p95 for messages **enqueued during t=[12,36) s**, supplemented by per-run p95s and uncertainty; report slowdown `[12,24)` and recovery `[24,36)` separately. Adaptive must improve p95 by >=20% versus fixed32, maintain 36-second worker completion throughput >=95% of fixed32, and keep whole-RPC elapsed time <=110% of fixed32; it must also show a useful tradeoff against fixed8, not merely outperform fixed32. Recovery is time from t=24 s until a 3-second continuous interval with queue-residence p95 <= the policy's own healthy `[0,12)` baseline p95 and throughput >=95% of its healthy baseline (where sufficiently sampled); if not achieved by t=36 s, report censored/not recovered. Never claim end-to-end latency improvement from queue-residence alone. Treat performance thresholds as practical thresholds, not significance tests.

**Stop:** stop implementation progression for incorrect ownership/accounting, gate deadlock, worker starvation in healthy load, uncontrolled budget oscillation, or invalid phase timing. Stop primary experimentation for resource guard trips or inability to complete/drain reproducibly; diagnose before resuming. Do not retune parameters after viewing primary results; any changes create a versioned exploratory follow-up. If fixed8 matches or dominates adaptive, explicitly report no demonstrated benefit and do not add worker concurrency to rescue the hypothesis.

## 7. Stage 1 acceptance and reproducibility

Stage 1 implements **measurement only**, with existing fixed bounded admission behavior; no adaptive controller yet. Required tests: (1) successful message handoff/dequeue/completion yields zero queue residence violations and exact counters; (2) capacity reservation occurs before receive and no read-ahead; (3) EOF with an unused reservation releases it and drains; (4) cancellation while waiting for capacity wakes and terminates; (5) cancellation during worker service accounts outstanding work once; (6) worker error wakes blocked handler; (7) queue/worker payload-byte ownership agrees with counts; (8) histograms yield correct known synthetic durations and phase assignment; (9) client scheduled/attempted/skipped/send-return counters balance; (10) repeated fresh-process smoke runs preserve one stream/connection and final Summary invariants.
